# Oracle harness sources

The unit tests in `internal/*` are pinned to vectors captured from the OpenJPEG
2.5.4 C reference and checked in under `testdata/vectors/`. Those vectors are
ground truth for the whole port, so the C programs that produce them are tracked
here rather than left in the gitignored `oracle/` scratch tree — otherwise
"regenerable" would be true only on the machine that first generated them.

Nothing here is part of the Go build: these are plain C sources plus a shell
script. `go build ./...` and `go test ./...` never look at this directory.

the reference (both reach into `static` C functions) and the exact record
formats they emit. Every `testdata/vectors/<module>/README.md` documents the
format of the vectors in that directory and which Go test replays them.

## Regenerating

```sh
# 1. Get and build the reference (static library + codec tools).
git clone https://github.com/uclouvain/openjpeg
cd openjpeg && git checkout v2.5.4
cmake -DCMAKE_BUILD_TYPE=Release -DBUILD_STATIC_LIBS=ON -DBUILD_CODEC=ON -B build .
cmake --build build -j

# 2. Regenerate into a scratch tree and diff against what is committed.
cd /path/to/gopenjpeg
OPENJPEG=/path/to/openjpeg tools/oracle-harness/regen.sh /tmp/vec
diff -r /tmp/vec testdata/vectors
```

`OPENJPEG` defaults to `<repo>/oracle/openjpeg`, which is where this repository's
own gitignored oracle checkout lives, so on a machine that already has the
oracle built the script needs no arguments. Run it with no `OUTDIR` argument to
overwrite the committed vectors in place.

Everything the script emits is byte-for-byte reproducible from the static
library except as noted below. One wrinkle for `diff -r`: the two `.gz` files
under `testdata/vectors/t1/` were compressed before this script existed and
carry a gzip timestamp, so their container bytes differ from a fresh run even
though the payload does not. Compare them decompressed:

```sh
cmp <(gunzip -c /tmp/vec/t1/t1_decode.bin.gz) \
    <(gunzip -c testdata/vectors/t1/t1_decode.bin.gz)
```

## What the script does not cover

**`testdata/vectors/mct/vectors.json`** regenerates, but four of its arrays —
`ict.enc_c0`, `ict.enc_c1`, `ict.enc_c2` and `ict.dec_c1` — will differ from the
committed file by 1–2 ULP on a minority of samples. The committed values come
from a build linked against the *shipped* `libopenjp2.so`, which OpenJPEG builds
`-O3 -ffast-math`; that reassociates the ICT terms (`y - u*a - v*b` into
`y - (u*a + v*b)`, and the forward grouping likewise), and the reassociated form
is what `opj_decompress`/`opj_compress` actually execute. `internal/mct`
reproduces the shipped form, so the committed vectors are the correct target.
See the provenance section of `testdata/vectors/mct/README.md`. Do not commit a
regeneration of this file without redoing that shared-library capture.

**`testdata/vectors/ht/*.gz`** need more than a compiler: apply
`w10/ht_dec_instrument.patch` to `src/lib/openjp2/ht_dec.c` in an OpenJPEG
checkout (it adds a dump hook at the tail of `opj_t1_ht_decode_cblk`, guarded by
the `OPJ_W10_DUMP` environment variable), rebuild, then decode the HTJ2K files of
the `openjpeg-data` corpus with the instrumented `opj_decompress` to capture the
cleanup-pass records, and feed the raw dump to `w10/gen_multipass.c` to
synthesize the multi-pass records. The full procedure, including the subsampling
step, is in `testdata/vectors/ht/README.md`.

**`testdata/vectors/jp2/golden.json`** is not a C harness product at all; it is
regenerated by a Go test:

```sh
GOPENJPEG_GEN_GOLDEN=1 go test ./internal/jp2 -run TestGenerateGolden
```
